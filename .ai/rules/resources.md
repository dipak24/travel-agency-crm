# Resources

## Tenant-owned models (BelongsToTenant) are invisible from the admin panel without withoutGlobalScopes()
Any model using the `BelongsToTenant` trait (TenantUser, Customer, TenantSubscription, etc.) has a global `TenantScope` that filters `where tenant_id = TenantContext::id() ?? 0`. The super_admin-guard admin panel never sets a `TenantContext` (only `ResolvePlatformTeam` runs, which sets the Spatie permission team id, not `TenantContext`), so any relation or query touching a tenant-owned model from an admin Filament Resource silently returns nothing (`tenant_id = 0` matches no real tenant).

Fix: add `->withoutGlobalScopes()` on the relation/query when it's meant to be read cross-tenant from the admin panel (see `Tenant::activeSubscription()`). To *create* a tenant-owned row from the admin panel (e.g. reassigning a `TenantSubscription`), you must wrap the create in `app(TenantContext::class)->set($tenant); ...; ->clear();` first — `BelongsToTenant`'s `creating` hook throws a `LogicException` otherwise, and force-overwrites `tenant_id` from the context even if you pass one explicitly.

Existing tests/seeders already work around this with `->withoutGlobalScopes()->where('tenant_id', ...)` — see `TenantOnboardingTest`, `PermissionSeeder`.

## A `date`-cast column is stored with a full `00:00:00` time suffix — exact-match `where()` against it silently finds nothing; use `whereDate()`
A model attribute cast as `'date'` (not `'datetime'`) only affects the *read* side — `$model->some_date` comes back as a start-of-day Carbon instance either way — but Eloquent's write path (`fromDateTime()`) still serializes it as a full `Y-m-d H:i:s` string (e.g. `'2026-10-01 00:00:00'`), confirmed via `getRawOriginal()` on both `Booking::$start_date` and `ServiceAvailability::$date`. A query built as `->where('date', $booking->start_date->toDateString())` (`'2026-10-01'`) therefore does an exact string/date comparison against a column actually holding `'2026-10-01 00:00:00'` and matches nothing — no error, the row is just silently never found (caught 2026-09-07 building `BookingAddonRequest`'s inventory check: a same-day `ServiceAvailability` row existed but the lookup always missed it). Fix: use `->whereDate('date', $booking->start_date)` instead of `->where('date', ...)` whenever comparing against a `date`-cast column — `whereDate()` normalizes both sides regardless of how the column is actually stored, across SQLite/Postgres/MySQL alike.

## Eloquent `create([...])` doesn't backfill DB column defaults onto the returned in-memory model
Creating a model via `Model::query()->create(['name' => 'x'])` and immediately reading an attribute you *didn't* pass (relying on the migration's `->default(...)`) returns whatever the attribute's cast produces from `null` — `false` for a `'boolean'` cast, `null` for most others — not the value the database actually stored, because Eloquent never re-fetches the row after insert. Caught 2026-09-07 two ways in the same session: a `Service::create(['name' => ..., 'price' => ...])` test helper read `$service->is_active` as `false` immediately after create (DB default is `true`), and an `Invoice::create([...])` without an explicit `currency` fed a stale `null` into a same-request `Payment::create(['currency' => $invoice->currency, ...])`, tripping the column's `NOT NULL` constraint. Any code that creates a model and uses one of its DB-defaulted columns in the same request — not just tests — needs either an explicit value passed to `create()`, a `->fresh()`/`->refresh()` call first, or (for the read side, cheaply) a `?? <default>` fallback at the point of use.

## Some architecture-doc table names don't pluralize the way Eloquent's convention would — set `$table` explicitly
`booking_include_exclude` (singular "exclude", per the architecture doc and its migration) is NOT what Eloquent's default naming convention produces for a `BookingIncludeExclude` model — `Str::plural()` pluralizes the *last* word, giving `booking_include_excludes`, which doesn't exist and throws `no such table` only once you actually query it (found 2026-09-07 building `BookingIncludeExclude` — Pint/static analysis won't catch this, only a runtime query will). Before trusting Eloquent's default table-name guess for a model backed by one of this app's architecture-doc tables, check the actual migration's `Schema::create('...')` name first, and set `protected $table = '...';` explicitly if it doesn't match what `Str::plural(Str::snake(class_basename))` would produce. Skim other multi-word architecture-doc table names (e.g. anything else combining a plural-looking word mid-name) for the same risk before assuming the convention holds.
